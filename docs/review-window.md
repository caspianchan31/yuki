# 等你审阅: where a proposal waits, the action review, drafts (v1.4)

History: v1.1 made a review nobody declined count as approved after 6 hours; reversed it (unanswered reviews expire unsent, aligned with Grok Bot). v1.4 keeps that and changes where a proposal waits, adds the action review and drafts. Requirement: nothing runs on the owner's behalf that they did not allow, by a click, by a rule, or by their own written sentences the review checks.

- **The card**: 允许一次 · 总是允许 · 拒绝 (`reviewCardView`, `packages/client/src/shell/chat/core.ts`, used by the review sheet on web and mobile). A draft (`isMessageToPeople(kind)`, `packages/domain/src/index.ts`: email now, Slack later by adding its kind to `messageKinds`) is marked `draft`: the card says 草稿 with 发送 · 不发, and 总是允许 unless it is a routine's.
- **Where it waits** (`ActionService.propose`, `actions.ts`; `AgentService.prepare`, `engine/service.ts`): a proposal of a task the chat started (the task has `originThreadId` and is not repeating, not a standing loop, not a routine; a routine is a repeating task carrying a `routine` field) has `noExpiry`: it waits until decided (`expiresAt` is then far off and unused; the line reads 等你决定). A background proposal (any `repeatMinutes`, a standing loop, a routine's) expires unsent `backgroundReviewMs` (30 minutes) after it was made. A card the person prepared themselves in the app (`POST /api/actions`) has no expiry. The worker's due review (`reviewDue` → `settleDueReview`, `engine/review-window.ts`) marks a background one expired; its task goes on told it was not sent (`approvalResult`).
- **Expired card**: 已过期，没有执行. Nothing can approve or decline it; 总是允许 is still offered and only saves the rule (`setReviewRule` does not run an expired action); 知道了，移出「需要你」 dismisses it.
- **Rules** (`POST /api/actions/:id/rule`, `AgentService.setReviewRule`; `review-rules` under the project's scope, id `<account id or project>:<kind>`, unchanged): 总是允许 saves `always` for that kind and runs the card's own action now; later ones of the kind run as soon as they are prepared (`autoApproved: "rule"`). `ask` (「以后都先问我」, still accepted by the endpoint; no button in v1.4) marks the card and later ones `askFirst`. The account's rule wins over the project's (`reviewRuleFor`). Never saved from a routine's draft (409).
- **Action review** (`review/action-review.ts`; settings `GET/PUT /api/review-settings` `{actionReview, askFirst[], autoAllow[]}`, per space, default on, at most 20 sentences each, 422 beyond): before a card is made, one model call of its own (no tools, the answer is JSON text, tolerant parsing, one retry, 60 s timeout, like `mail/claim-check.ts`) says which sentences matched, `lowRisk` and a reason. The server decides, in this order: an 先问我 sentence matched → ask (wins any conflict, even over 总是允许); else a 总是允许 rule for the kind → run (`autoApproved: "rule"`); else an 自动放行 sentence matched, or `allow` for a low-risk action → run at once, `autoApproved: "review"`, `reviewReason` kept and told to the run; else ask. A message to people is never let through by the reviewer's judgment alone, only by an 自动放行 sentence or 总是允许. A failing, timed-out or unreadable review → ask. Review off → ask unless a 总是允许 rule covers the kind. The model is not called when its answer cannot change the outcome (review off; a message with no 自动放行 sentence; 总是允许 with no 先问我 sentence). A card that asks keeps the reviewer's reason (`reviewReason`).
- **Routine drafts**: no rule and no review lets one go, it never expires, and its run does not wait on it: `prepare_email` answers `draft_waiting` (the run goes on and says in its summary that the draft is waiting; the task gets no `actionId`). The card stays among 需要你 until 发送 (it sends even after the run ended) or 不发.
- What a decline does: nothing is sent and the task goes on told so. For a message to people it is final (docs/mail.md): a new message to the same recipients in the same run is refused by the server, so the run does not retry, reword or reach them another way; it tells the person it did not go out. Other kinds of action keep the old way (the run may change and prepare again).
- Settings sheet saves go out one at a time in the order made, and only the newest answer reaches the screen (`serial-save.ts`); quick edits never lose a sentence.
- Settings: 动作审查 switch and the two lists (add, edit, delete, count shown, 20 cap) on the settings sheet (`apps/web/src/panels/task/ReviewSettings.tsx`).

Tests: `tests/action-review.test.ts` (a decline or expiry of a message is final, decision order, conflict, 20 cap and 422, failure asks, messages never by the reviewer alone, chat vs background expiry, expired 总是允许, routine draft), `tests/review-blacklist.test.ts` (background expiry, decline, rule at once, rule scope), `tests/actions.test.ts`, `apps/mobile/test/shell-chat.test.ts` (the lines and buttons).
