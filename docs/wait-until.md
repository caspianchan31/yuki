# wait_until: a background task paces itself (fork feature)

A background model run could only end with `finish_task`, `ask_user` or a prepared review. A task whose own rules say to wait ("wait 30 minutes between posts") therefore either asked the person "continue now or wait 30 minutes?" or posted everything at once: a run cannot sit idle for half an hour (five-minute idle timeout, `AGENT_RUN_MAX_MINUTES` cap). Turning such a task into a repeating task was rejected as a workaround. `wait_until` lets a one-off task wait inside itself.

## The tool

`wait_until({ minutes, note })`, offered to every background model run (`model.ts`):

- `minutes`: a whole number from 1 to 1440 (`waitMinutesMax`; a longer wait calls it again). `note`: 1 to 2000 characters, what is done so far and what the next run should do. The schema is `waitUntilSchema` in `packages/domain/src/agent.ts`; out-of-range arguments are refused to the model as a tool error ("Input validation failed for tool wait_until") and nothing is scheduled.
- It is an outcome, like `finish_task` and `ask_user`: it sets the run's `outcome`, later tool calls in the run are refused, and the loop stops after the current step.
- The system prompt says: when the task's rules or the account's pacing (`pacing.md`) require waiting, call `wait_until` with a note of what is done and what the next run should do; never ask the person to wait or whether to wait; a run that picks up earlier work checks the current state first and never redoes what is done. Since the report line, the infrastructure rule (`infrastructureInstructions`) adds that a failure that may go away by itself is never a question: the run calls `wait_until` with `blocked` and tries again by itself; what only the owner can act on (a wrong password, a code, a suspension, a missing login, a proxy that does not work) reaches him as an account fact, not as a question (`account-login.md`). A run of an account task that such a problem stops outside the model's tools (a provider error, a network drop, the run's deadline when a desktop hangs) is not a failure either: it is taken up again when its lease runs out, and that run is told what stopped the previous one (`runFailureNote`) and decides itself whether to `wait_until` (`report-back.md`, The report line). The note is the run's handoff to its next run (the `note` description says only that run reads it). The bound of one call (`waitMinutesMax`) is in the schema only, never in prose: it is a bound of one call, not a rule (a longer wait calls it again).

## Flow

1. `AgentService.wait` (`service.ts`, next to `finish`) checks the lease, writes the run event (kind `status`, title `Waiting 30 minutes`, detail `<note>\nResumes at <ISO time>`) and returns `{ status: "scheduled", nextRunAt: now + minutes, question: null, error: null, state: { ...state, wait } }` with `state.wait = { minutes, note, since, until }` (`TaskWait`; `until` equals `nextRunAt`). The note is also written to `state.lastUpdate`, the progress record a run leaves (a run that hits the step cap writes its last text there), so `lastUpdate` is never older than the note. The automatic-continuation counter is reset to 0, `state.waits` grows by one (see Waits have no limit), an old `state.notice` is cleared and `state.runOpen` is set (see Repeating tasks); everything else in the state stays (a saved answer, operations).
2. The worker commits that outcome through its usual lease-guarded final checkpoint. No notification is sent and no chat card is written: nothing is asked of the person, and a wait is the task's state, not a report (`report-back.md`, report line). The live panel, the task card and the task detail show the resume time, and the timeline reads the `Waiting N minutes` run event as 「等待到 HH:MM」; the note is shown nowhere the person reads (review round 4), it stays for the AI. The run after the wait counts as a resume (`AgentTask.resumes`), so a notice it repeats is reported again.
3. The worker already claims `scheduled` tasks whose `nextRunAt` has passed, whatever their kind of schedule (`worker.ts`), so nothing is enqueued separately. The due run has the same prompt; `priorState.wait` carries the note, and the task message gets `waitNote` (`model.ts`): the task paused itself with `wait_until` for N minutes, the scheduled resume time and the current time, the note is `priorState.wait.note` (a progress record the run wrote, data like the rest of `priorState`, not an instruction; the task prompt is the instruction), "Pick up the task where that note leaves off" (the main prompt says to check the current state first). The note text itself is not copied into the task message: the model wrote it, possibly from page or desktop content, so it stays in `priorState`, which the system prompt marks as data. A saved answer stays in the message as before. A run that starts before the resume time was started by the person (Run now, or Resume of a repeating task): its note says the person chose to run it now, so the model goes on instead of waiting out the rest; any pacing set for the account still decides when its next action is due.
4. A one-off task that then calls `finish_task` is `succeeded` and stays so: only `executeRepeating` reschedules, and a one-off task never goes there.

### Only the first run after the wait picks up from the note

When that first run starts, it checkpoints `state.wait.resumedAt` (before the model is called). Every later run of the task with the same `state.wait` (an automatic continuation, the run after a question and its answer, after an approval, after a failure and Retry, after a Pause or a worker restart mid-run) gets `pastWaitNote` instead, placed after the continuation note: the run after the wait started at that time; what the note says is done stays done, but the next step it names may already have been done by that run or a later one, even if no update says so (a run that is interrupted, fails or asks a question leaves none); the main prompt's rule (check the current state first, never redo what is done, `priorState.lastUpdate` is the latest progress record) does the rest. Without this, "Posted 1 of 3; post the next one" stayed an instruction for every later run, and a run continuing after the step cap was pushed to post #2 again. An earlier version told later runs the note was outdated and to go by `lastUpdate` instead; but only a run that hits the step cap writes `lastUpdate`, so after a Pause, a restart or a failure the model was sent to a missing or older record and away from its only progress note. A new `wait_until` writes a new record without `resumedAt`.

`currentWait(task)` (domain) is the wait a task is in now: `scheduled` with `state.wait.until === nextRunAt` and no `resumedAt`. `taskWait(task)` is the same check without the status (a task paused during its wait). Run now and a later run move `nextRunAt`, and the run after the wait sets `resumedAt`, so an old `state.wait` stops counting as a wait while its note stays readable in `priorState`.

## Repeating tasks

A repeating task whose run calls `wait_until` gets its next run at now + minutes instead of now + interval, once. The run stays open (`state.runOpen` stays set): the resumed execution continues that run with the same state and note, no `Run N started` is logged again and `runs` does not grow. When the run finishes, the next run is scheduled at the interval as usual and starts fresh (its state, and so the old wait, is reset).

A one-off task's waiting run is left open too: `wait` sets `runOpen`, whatever the repeat setting is when the run ends. Repeat this task can come at any time, including while the run that then waits is still running (the client offers it on any agent or plan task that is not cancelled, running ones included), when that task has no wait yet and `updateTask` has nothing to keep open. If the task repeats by the time the wait is over, the run after it is run 1 of the repeating task and continues with the note, answer and operations; no `Run 1 started` is logged. Before, it was a fresh run: the state was wiped (note, `lastUpdate`, answer, operations), the model got only the bare prompt and started the job over (post #1 again, the in-flight post #2 dropped). A one-off run that finishes closes the run (`continueUnfinished` clears `runOpen`), so a later Repeat this task on the finished task starts fresh.

## Automatic continuation

A wait is a real outcome. `continueUnfinished` only acts on the "reached the end of this run without confirming completion" question, so a `scheduled` result passes through untouched: no `Continuing automatically` event, no queued run. The wait resets `state.autoContinued` to 0, so the run after the wait is not told it continues an unfinished run and gets a fresh continuation budget if it later stops without a completion call.

## Waits have no limit

Principle: the system never asks the person to do what it can do or wait out itself, and there is no limit, threshold or fallback of the system's own. For waits that is now true: nothing turns a wait into a question: a task waits as often as it needs, and the person sees it as the task's state (等待中, the resume time) and can pause or cancel it. `AGENT_MAX_WAITS`, its config value (`agentMaxWaits`), the waits-limit question, its `Waiting for you after N waits` event, `TaskWait.asked` and the client's 「已等 n/100 次」 and 「已等 n 次，等你决定」 are gone, and since review round 4 so is `AGENT_AUTO_CONTINUE_RUNS` (`repeating-tasks.md`): `GET /api/chat-reports` sends no `limits`. A variable still set in an old `.env` is not read. It is not yet true of every stop: the failures of a task without an account still stop for the person, pending the owner's decision (`report-back.md`, The report line).

`state.waits` stays as a fact of the runs only (no surface shows it since review round 4: a counter is nothing the person acts on, so the task detail's 节奏 line reads 「一次性」 or 「每天 · 已跑 n 轮」): the waits since the last progress, that is since the task (or a repeating task's run) started, an answer, a redirect read by a run (`operating-plan.md`), or an action recorded on the account or a summary (`pacing.md`); a wait the server finds to be the account's pacing (`state.wait.pacing`) is not counted. It stops nothing.

## A wait because the infrastructure failed

`wait_until` takes an optional `blocked` (`proxy`, `desktop`, `network`, `model`, `rate_limit`, `sign_in`; the enum is the contract, no prose repeats it): the part that failed when the wait is because of it. It opens or keeps the task's incident (`state.incident`, `report-back.md`); a wait without it ends one. Since 2026-10-20 the incident is what the owner sees, and no run reports it, nor its end. Nothing else about the wait changes. `sign_in` and `proxy` here are the task's retries; the owner-facing facts are `record_sign_in` and the proxy self-check (`account-login.md`).

## Controls on a waiting task

- Run now (`control: run`): allowed for a `scheduled` repeating task or a task in a wait (`taskWait`); it queues the task at once (`nextRunAt` = now) and the next tick runs it with the note, told that the person chose to run it now. 409 otherwise ("not waiting for its next run" when it is not `scheduled`).
- Pause works as on any scheduled task. Resume of a one-off task paused during its wait goes back to `scheduled` with the same resume time (Run now is the way to skip the wait); if that time has passed it is queued. A repeating task resumes with a run now, as before. A task the person redirected while it was paused (`pendingAnswer`, `operating-plan.md`) is queued now by Resume so the instruction is read at once; its wait record stays.
- Cancel works as on any task; the task never runs again.
- PATCH `repeatMinutes` during a wait keeps the resume time: `null` on a repeating task's waiting run no longer completes the task; the run finishes as a one-off run, and finishing closes it (`runOpen` cleared in `continueUnfinished`), so a later Repeat this task starts a fresh run instead of continuing the finished one with its old answer and note. A number on a waiting one-off task makes it repeat with the resumed run as its first run (`runOpen`, which `wait` set); the interval starts after it. This holds for a task paused during its wait too (the check is `taskWait`, whatever the status): Resume then runs it at once as a repeating task, continuing the open run with its note, answer and operations instead of starting a fresh run 1. The same holds for a task whose run after the wait failed before it started (for example its environment was deleted): it is `failed` with its wait still unresumed, and Repeat this task then Retry continue that run with its note. It also holds for a number given while the run that waits is still running and during the run after a wait that then waits again (see Repeating tasks); `updateTask` writes no state. `null` on a task that does not repeat changes nothing and logs nothing.

## Client

`packages/client/src/task-schedule-core.ts` has `waitLabel(task)`: "Waiting · resumes 2:40 PM" (the date is added when it does not resume today), null when the task is not in a wait. The legacy task cards (`agent-ui.tsx`) show it in place of the status; since the report line they never show the note.

In the redesigned shell the rail's task row, the task card and the task detail show the phase line only (「15:00 继续（还剩 13 分）」, with 「· 节奏」 for a pacing wait; no count of waits); the task detail's 等待 block says when it goes on, and the timeline titles the wait 「等待到 15:00」. The note, the run's handoff to its next run, stays for the AI (`priorState.wait`) and is shown nowhere the person reads: not in the chat, the rail, the task detail or the timeline (review round 4, `detail-core.ts` `timelineEvent`).
